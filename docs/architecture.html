Comment organiser des agents Claude quand on porte plusieurs portefeuilles de projets. Ni une équipe unique qui « fait attention », ni une copie de l'équipe par projet. On sépare trois choses qu'on mélange souvent : qui est l'agent, où il travaille, comment il agit. Chacune a sa place, et le cloisonnement se fait par les accès, pas par la consigne.

Décider vite

Où va cette skill ?

Livre ou skill

Le livre explique, la skill exécute

Livre · savoir à lire

  • Le pourquoi : raisonnement, hiérarchie des preuves, niveaux de risque.
  • Long, lu par chapitre via le sommaire.
  • Évolue par proposition acceptée, suivi par version.

Skill · geste à exécuter

  • Le comment : étapes, scripts, critère de fin.
  • Court ; seule sa description est chargée tant qu'elle ne sert pas.
  • Déclenchée par la situation, sans qu’on ait à la nommer.

Concrètement : les WF-01 à WF-13 du profil DevOps (analyser une infra, déployer, rollback…) sont des skills qui s'ignorent. Le livre garde le raisonnement et renvoie à la skill ; la skill renvoie au chapitre pour le pourquoi.

Pas de bibliothèque plate : un plugin par rôle ou par plateforme, et chaque cluster n'active que ceux qu'il utilise. Deux skills qui se ressemblent font choisir la mauvaise.

Anti-contagion

Cloisonner par les accès, pas par la consigne

Tient tout seul

  • Une distro par agent, au cluster de l'instance, sans /mnt/c ni interop.
  • Un jeton fine-grained limité aux repos du cluster.
  • Secrets nommés par la seed du cluster, absents ailleurs.
  • MCP déclarés dans le .mcp.json du cluster, jamais en scope user.
  • Refus par défaut sur la prod, hook qui vérifie l'environnement cible.
  • Mémoire d'équipe dans le repo du cluster.

Ne tient pas seul

  • « Sois conscient du contexte » dans un prompt.
  • Un CLAUDE.md global qui parle de projets.
  • Un serveur MCP de déploiement installé pour tout le poste.
  • Un jeton d'organisation : un agent explore ce que son jeton lui ouvre.
  • Une Cantina commune à tous les clusters.
  • Une session longue qui passe d'un cluster à l'autre.

Une skill de déploiement du cluster A lancée par erreur ailleurs échoue d'elle-même : ni le jeton, ni le secret, ni le MCP n'existent dans l'autre distro. C'est le comportement voulu.

Découper

Quand faire une nouvelle instance d'équipe

Nouvelle instance si un seul de ces points est vrai

  • Les secrets ou les comptes cloud sont différents.
  • Le propriétaire ou le client est différent.
  • Les données sont réglementées ou sensibles.
  • Une fuite de nom de repo serait un problème.

Même instance, un contexte par repo, sinon

  • Un cluster de petits SaaS : une équipe réduite (PO, lead tech, DevOps) pour tous les SaaS.
  • Conventions et plateforme communes dans petits-saas-hq.
  • Une session par SaaS, jamais deux SaaS dans la même session.
  • Un SaaS qui grossit ou prend un client sort en cluster.
La méthode

Un chantier, de la demande à la livraison

Une équipe qu'on lance sur un grand chantier se met vite à parler en même temps, dans tous les sens. L'orchestrateur de l'équipe livrée ne délègue rien avant d'avoir planifié, et ne fait intervenir la recette et la sécurité qu'à des moments précis. Le livre equipe/table le dit pour les agents ; la skill koa:mener-un-chantier en donne les gestes.

  • L'inventaire
    Qui est à la table, et combien de chaque rôle : deux agents du même rôle sont deux files de travail. Une présence ne se suppose jamais.
    cantina_tables
  • Le tour de table
    Une CONSULTATION aux spécialistes, un AVIS de chacun — découpage, dépendances, risques, choix à trancher —, et pas de débat.
    avant toute mission
  • Le plan en vagues et son Gantt
    Soumis une fois à l'humain avec toutes les décisions qu'on voit venir, tenu à l'heure réelle au QG, dans docs/chantiers/<chantier>/.
    PLAN · à valider
  • Les missions
    Une fiche par mission, commitée au QG ; le message n'en donne que l'adresse. En mission, on ne joue que les tests de ce qu'on touche.
    MISSION · RÉSULTAT · REVUE
  • Finaliser une feature
    Elle entre dans develop, et c'est le seul moment où tout se rejoue : suite complète, recette au navigateur si un parcours change, sécurité si la surface change.
    FINALISATION
  • Livrer
    develop sur master, sur l'ordre de l'humain seulement : le SecOps passe toujours, le DevOps monte la version de chaque composant touché.
    LIVRAISON
Dans KoA

Ce que KoA porte pour vous

  • Le livre koa/architecture
    Ce framework expliqué à vos agents, un chapitre par question, versionné dans la librairie.
    disponible
  • Les rôles de l'équipe
    PO, lead tech, qualité, DevOps, sécurité, orchestrateur, et leurs contrats : equipe/*, lus par vos agents au lieu d'être recopiés.
    disponible
  • Une distro cloisonnée par instance
    Une seed fait naître une distro dédiée, sans disque Windows ni interop, avec ses secrets et un jeton limité à ses dépôts.
    disponible
  • La marketplace koa-skills
    Skills de rôle, plugins de plateforme, garde-fou de déploiement, épinglés par version : Happykiller/koa-skills.
    disponible
  • Le QG d'un cluster, monté par une skill
    CLAUDE.md, KB, plugins épinglés et refus par défaut, remis d'aplomb sans rien écraser : koa:monter-le-qg.
    disponible
  • Une Cantina par cluster
    Un agent ne voit et n'adresse que les agents de son cluster ; vous les voyez tous. Le champ cluster d'une seed l'active.
    disponible
  • Un coffre par cluster
    Ce qu'aucun repo ne doit tracker — kubeconfig, comptes, clés, jetons —, chiffré sur le poste. Un agent le dépose dans sa distro sans en voir la valeur, publie ce qu'il crée, et une seed y puise à la naissance. Vous le gérez depuis la carte du cluster.
    disponible
  • La méthode de chantier
    Inventaire, tour de table, plan en vagues, finaliser et livrer : dans les livres de l'équipe et la skill koa:mener-un-chantier.
    disponible
  • L'audit d'une table
    « Auditer… » sur une table de la Cantina : ce qui s'est dit, ce que chaque agent a fait outil par outil, et les constats mesurés, dans une rétrospective prête à rédiger.
    disponible
